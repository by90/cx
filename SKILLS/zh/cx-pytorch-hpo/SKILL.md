# cx PyTorch 自动 HPO

## 目的

把候选方向、参数碰撞和训练资源分配交给可恢复、可审计的 HPO 工具，避免代理沿错误方向手工连续调参。不区分轻量与全量阶段，不抽取十分之一实体，不使用严格测试选择参数。

## 不可变约束

1. 先读项目 `AGENTS.md`、实际配置、公共训练/调参入口、调用方、测试、冻结基线和真实产物。已有模型无关调参模块时演进它，不在模型目录复制生命周期。
2. 股票调参使用适用注册制生效日起的全部合格实体和日线；创业板默认起点为 `2020-08-24`。资源不足不得改变股票覆盖。
3. 标签、级别、排序分数、TopN/Top10 和切分来自项目权威入口。窗口变化时固定 validation/test 目标日期边界。标签或业务口径变化必须建立独立 study，不直接排名。
4. 验证业务指标是 sampler、pruner 和 incumbent 的目标。验证损失只用于梯度、诊断和规定检查点；不得仅因损失下降晋级。
5. 严格测试不进入 study、中间值、剪枝、参数重要性或下一配置。最终只审计验证选择的 incumbent；若测试参与选择，立即声明污染并停止。
6. 明确使用成熟 HPO 工具。单机 PyTorch/Lightning 默认优先 Optuna；若改用 Ray Tune、Syne Tune、SMAC 等，先以官方文档核对系统支持、进程/内存成本、恢复存储、条件空间、并行 sampler 和多保真剪枝，再记录选择理由。
7. 自动 HPO 不固定每个 trial 的训练轮数或 patience。关闭 Lightning 等框架的人工原生早停，由 pruner 根据逐轮验证业务指标决定停止。允许设置硬件、墙钟和安全所需的全局资源轴上界，但 trial 不必跑满。
8. 搜索范围不能缩成 latent 宽度。按任务覆盖数据/窗口、字段表示、时间模型、纵横摘要、优化器、学习率、weight decay、批次、调度器及其 warmup/周期/min-lr/restart、dropout 和损失；用户冻结项不得进入搜索。
9. 使用 define-by-run 条件空间：只有被选中的优化器、调度器、结构或损失才采样其有效参数；结构组合必须满足整除、形状和显存约束。类别权重已被项目证据否定时不重复搜索。
10. 多 GPU 每张卡同时只运行一个独立 trial worker。启动前用真实张量估算 VRAM、系统内存和每轮时间；本地多进程使用官方支持的共享存储，不以复制大规模 Ray 运行时换取无效复杂度。
11. 每轮记录训练/验证损失、累计业务最优、学习率、耗时、步数、显存和必要的系统内存。每个 trial 冻结实际配置、逐轮轨迹、业务最优、validation-loss 最优和剪枝/完成时最终状态；OOM 和异常作为显式 trial 状态与失败原因。
12. `1` 个百分点等最小有意义差异只用于两个已完成、同口径 trial。一次训练内只报告业务最优值/轮次和 validation-loss 最优值/轮次，不描述“之后改善不足阈值”。

## 公共模块协议

公共调参模块唯一负责：

- 创建或恢复持久化 study，冻结工具版本、sampler、pruner、随机种子、目标方向、资源策略和数据摘要。
- 将 HPO 提议转换为类型化内存配置，不改写产品默认配置，不通过命令行暴露实验参数。
- 把逐轮累计验证业务最优交给 pruner；HPO trial 关闭框架原生人工早停。
- 管理每个 trial 的独立产物目录、GPU 身份、状态、检查点、资源事实和恢复。
- 持续生成 `analysis.json` 与 `analysis.md`，列出完整/剪枝/失败/运行中 trial、incumbent、参数、实际轮数、资源、失败和参数重要性。
- 保证 sampler/pruner 运行期间代理不手工覆盖下一配置、轮数或停止决定。

模型薄封装只声明网络、损失和搜索空间。禁止保留旧的 QuickTune、人工单候选审批、固定 `1000/20` 合同或新旧双协议；旧人工实验只在结果说明中作为历史事实。

## 实施流程

1. 冻结数据范围、validation/test 日期边界、标签、业务目标、硬件/墙钟限制和禁止搜索项。
2. 联网比较当前工具；本地双 GPU PyTorch 通常选择 Optuna 多变量 TPE（条件/联合空间）与 Hyperband/Successive Halving（多保真停止），并说明为何不叠加更重的调度框架。
3. 以 TDD 接通公共 trainer 的逐轮 observer、工具剪枝异常、三权重、持久化共享存储、恢复和分析文件。先用独立基础设施冒烟验证多进程锁，不用缩小股票池伪装正式 trial。
4. 建立完整搜索范围。连续参数使用合理线性/对数分布；离散窗口或结构用 categorical；不假定非单调业务目标可二分。
5. 固定种子和 study 名；两个 GPU 各启动一个 worker。让 sampler 提议配置、pruner 决定实际轮数，不在运行中人工改方向。
6. 持续检查目标、资源、OOM、僵尸 trial、存储和产物，不用 strict test。失败时修复基础设施后恢复同一 study，不能删除不利 trial。
7. 只有 study 达到预定墙钟/收敛停止条件后才冻结 incumbent；必要时用独立种子复现。最后只用项目规定的 validation-loss 检查点执行一次严格测试和回测。

## 极端不平衡目标

- 九级分类保存逐类支持、混淆、最高两级精确率/召回率、预测覆盖、收益、尾部风险和逐日稳定性；总体准确率不能替代业务目标。
- 多分类、序数、成对/listwise 排序和可微 Top-K 可以成为条件损失空间。不同标签或业务定义必须使用独立 study；不同损失的数值不直接比较，但同一业务指标可以比较。
- 对业务目标上报累计最优可降低瞬时波动对多保真剪枝的误导；原始逐轮值仍须完整保存。

## 轨迹分析工具

运行：

    python scripts/analyze_hpo_progress.py path/to/ledger.json path/to/analysis

台账包含 `data_scope`、`optimizer`、`objective`、`resource_policy`、`trials` 和 `strict_test_used_for_selection`。`optimizer` 记录工具、sampler、pruner 和持久化存储；trial 记录 `number/state/value/params/intermediate_values/completed_epochs` 以及验证、资源、失败和产物事实。

工具只验证和汇总当前 study，不替 sampler 选择下一配置。输出必须包含状态计数、incumbent、实际轮数、失败原因和可用的参数重要性，并证明严格测试未参与选择。

## 完成证据

- 工具选择的官方依据、公共模块与调用方审计、旧协议物理删除。
- 注册制起点、全部合格实体数、日期边界、数据版本和内容摘要。
- sampler/pruner/存储/资源策略、完整条件搜索空间和用户冻结项。
- 双 GPU 并发存储冒烟、每轮轨迹、trial 状态、实际配置、权重与持续分析。
- 当前 incumbent 的验证业务结果和独立复现；最终严格测试及其未参与搜索的证明。
